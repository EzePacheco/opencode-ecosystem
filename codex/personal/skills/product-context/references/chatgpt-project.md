# Space, Project and engineering handoff

Use this reference when deciding where durable Product knowledge belongs or
whether an engineering handoff needs Product context.

## Responsibilities

- **ChatGPT Space / designated Pages** — durable Product knowledge home and
  Product Authority only when the Product explicitly designates it, and only
  for the Pages and scopes with adequate provenance and current status.
- **ChatGPT Project** — orchestration, Project instructions, governance
  sources, and only the minimal Product bridge actually needed for work in that
  Project. A Project bridge is derived working context, never authority.
- **Codex** — repository/runtime Technical Truth from current implementation
  evidence. Codex Local does not automatically receive Space, Project, Sources,
  Library or chat content.
- **Engineering handoff** — explicit transfer by the orchestrator of material
  Product decisions, or references to canonical sources that Codex can
  actually access. Do not assume the bridge itself reaches Codex.

Products need not adopt Space. Continue using each Product's designated
existing authorities where Space has not been adopted or a scope has not been
migrated. A Space can be a durable home without every Page being authoritative;
designation, provenance, status and scope still matter.

## Notion-to-Space migration

Use INGEST / RECONCILE to classify supplied Notion material and map durable
Product knowledge semantically to candidate Pages or other appropriate
destinations. Keep current authority, current reference, proposed/discovery,
historical/superseded, duplicate and VERIFY distinct. Preserve source
provenance and identify unmigrated scopes. A source manifest is optional and
only useful when multiple sources require mapping.

Migration may be partial. Notion remains authoritative for each scope until
explicit Product-authority cutover for that scope. Page creation or content
transfer alone does not enact cutover. See [workflows](workflows.md) for
migration inclusion and application rules.

## Minimal Project bridge

Create a bridge only when the active Project has a real Product-context or
source-access gap. Prefer canonical Page references over copied Product
content when the Project surface can reliably use them. Include only the
identity, canonical home, relevant authority references, material active
decisions, open VERIFY, repository map or migration status needed for the
Project. Do not define a universal filename or output location; do not
duplicate the Product source of truth.

When Product decisions must inform repository work, have the orchestrator
explicitly transfer the material decisions to Codex or provide accessible
canonical references. Do not route Codex to reconstruct private ChatGPT
context unless the user explicitly requested that particular retrieval and
purpose.
